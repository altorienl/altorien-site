## Technical SEO audit

TECHNICAL SEO AUDIT — altorien.com (verified live 2026-11-01, read-only, nothing deployed, repo left clean)

WHAT I COULD NOT AND DID NOT CHECK: I did not observe Google's index or any SERP. I make no claim about whether altorien.com is currently indexed, and nothing below is a promise about ranking. Everything here is standard Google Search Central practice: no keyword stuffing, no structured data asserting anything not visible on the page.

=====================================================================
A. WHAT IS ALREADY CORRECT (measured, not assumed)
=====================================================================
- HTTPS is correct. TLSv1.3, cert CN=altorien.com from Google Trust Services, valid to 2027-01-29, curl verify result 0. HSTS present: max-age=15552000; includeSubDomains. http://altorien.com/ 301s to https.
- Both target pages return 200: https://altorien.com/ (62,202 bytes) and https://altorien.com/resume (19,853 bytes).
- No stray noindex anywhere. Zero robots meta tags, zero X-Robots-Tag headers on /, /resume, /lander/ or /robots.txt.
- robots.txt is 200, 23 bytes, "User-agent: *\nAllow: /". It blocks nothing. No render-critical resource is disallowed: CSS is inline in each HTML file, the only JS is inline, and all 11 referenced images plus /contrib.json return 200.
- Canonicals are present, singular and correct on all four URL variants served (exactly one <link rel="canonical"> per document; apex, www and /lander/ all point to https://altorien.com/, and /resume points to https://altorien.com/resume).
- The resume is reachable by a crawlable anchor from the homepage: <a href="/resume">Resume</a> in the nav. Plain href, no JS, no onclick.
- Important text is in the HTML, not injected by JS. The homepage ships 276 words of server-rendered text including the full employment history. The contribution graph is baked in at deploy time and the JS only refreshes it; with JS off the page is complete.
- No cloaking and no bot blocking. A Googlebot user agent receives byte-identical responses to a desktop Chrome user agent on both pages.
- Mobile rendering is clean. At 390x844 with deviceScaleFactor 2 (viewport verified to innerWidth exactly 390 before measuring) both pages have scrollWidth == clientWidth, zero overflowing elements, and a correct <meta name="viewport">.
- /projects and /projects/* 301 to / as intended. Unknown paths return a true 404, so there is no soft-404 risk.

=====================================================================
B. THE www / APEX SITUATION, AND THE RIGHT FIX
=====================================================================
Measured: https://www.altorien.com/ returns 200 with bytes identical to https://altorien.com/ (cmp reports no difference). There is no redirect between them. http://www 301s only to https://www, staying on www. wrangler.toml declares both as custom_domain routes and src/index.js has no hostname check, so the Worker serves both hosts the same assets.

What that means for indexing: you are serving the same document at two hostnames. Google will pick one as canonical and the other as a duplicate. Your canonical tag on the www copy already points at the apex, so the signal you want is being sent. But rel=canonical is a hint, not a directive. Google can and sometimes does choose differently, external links split between the two hosts, and Search Console reports the two separately. Note also that the "preferred domain" setting was removed from Search Console in 2019, so this cannot be fixed in the dashboard.

The right fix is a server-side 301 from www to the apex, keeping the canonical tag as a backstop. Five lines in the Worker you already own, version controlled, no dashboard state. In /Users/alockwood/altorien-site/src/index.js, inside fetch(), immediately after `const url = new URL(request.url);`:

    /* One hostname is the site. www 301s to the apex with path and query
     * intact, so Google is never asked to choose between two identical
     * copies. The route stays in wrangler.toml: removing it would make
     * www stop resolving, which is worse than a redirect. */
    if (url.hostname === 'www.altorien.com') {
      url.hostname = 'altorien.com';
      return Response.redirect(url.toString(), 301);
    }

Keep the [[routes]] block for www.altorien.com. Deleting it would break www entirely rather than redirect it. The dashboard alternative is a Cloudflare Redirect Rule (Rules > Redirect Rules) matching http.host eq "www.altorien.com", but the Worker version is auditable in git, so prefer it.
